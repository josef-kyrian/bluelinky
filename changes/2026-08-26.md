# Task: implement current EU OneApp/CCI authentication in bluelinky

We are working in a fork of the official `Hacksore/bluelinky` repository.

The goal is to make the current Bluelink API work again for EU Hyundai accounts while preserving the existing public `bluelinky` API.

Do **not** base the implementation on `PierreLevres/Kuvork`. The official upstream is now the base because it already contains newer CCS2 support.

## Goal

A normal user of the library should still be able to do essentially this:

```js
const client = new BlueLinky({
    username: process.env.BLUELINK_USERNAME,
    password: process.env.BLUELINK_PASSWORD,
    pin: process.env.BLUELINK_PIN,
    brand: 'hyundai',
    region: 'EU',
});

client.on('ready', async () => {
    const vehicles = await client.getVehicles();

    console.log(vehicles);
});
```

No manually generated refresh token should be required.

No ioBroker-specific wrapper should be required.

No `autoLogin: false` + manual controller/session injection should be required from the library user.

The new EU login should happen internally as part of the normal Bluelinky authentication flow.

---

# Background

The old EU authentication used by Bluelinky/Kuvork is obsolete.

Current working implementations use the newer Hyundai/Kia **OneApp / CCI authentication flow**.

The important reference implementations are:

1. `Newan/ioBroker.bluelink`
   - especially `lib/tokenManager.js`
   - current implementation has been tested against a real EU Hyundai account
   - this is the primary JavaScript reference

2. `Hyundai-Kia-Connect/hyundai_kia_connect_api`
   - current Python implementation
   - use this as a second independent reference for protocol details

3. `TMA84/bluelink-refresh-token`
   - another implementation of the current CCI authentication
   - useful for comparing token handling

Do not blindly copy old Bluelinky/Kuvork login code.

---

# Important architectural point

`Newan/ioBroker.bluelink` is **not** a replacement for Bluelinky.

It still uses Bluelinky for vehicle communication.

Because it cannot modify Bluelinky itself, it currently does roughly this:

```text
perform CCI login externally
        ↓
obtain current CCS access token
        ↓
create BlueLinky with autoLogin=false
        ↓
inject token into Bluelinky controller/session
        ↓
replace Bluelinky refresh logic
        ↓
use normal Bluelinky vehicle API
```

We own this fork, therefore we should **not reproduce that external monkey-patching architecture**.

Instead, integrate the CCI authentication properly into Bluelinky's own authentication/session architecture.

# Token model

The current authentication model is no longer just:

```text
accessToken
refreshToken
```

and specifically it is no longer valid to treat a manually generated refresh token as the account password.

The CCI refresh process requires a collection of related tokens.

Inspect the current reference implementations and create an explicit typed representation for the complete token state.

It currently includes values conceptually corresponding to:

```text
CCS access token

CCI refresh token
CCI access token

exchangeable token
exchangeable refresh token

non-CCS token
non-CCS refresh token

ID token
```

Use the exact names/semantics used by the current API after verifying the reference implementations.

Do not throw away token fields that are required by the CCI refresh endpoint.

# Session integration

Integrate the resulting authentication into Bluelinky's existing session.

The CCS access token obtained from the CCI token exchange should become the token used by the existing European vehicle API.

The general idea should be:

```text
CCI authentication
      ↓
Bluelinky session populated
      ↓
normal getVehicles/status/control API
```

Avoid exposing CCI implementation details to normal Bluelinky users.

If necessary, extend the existing `Session` type with CCI-specific state, preferably grouped rather than dumping many unrelated properties into the root session object.

For example conceptually:

```ts
interface CciTokenSet {
    // exact fields determined from current protocol
}

interface Session {
    accessToken?: string;
    refreshToken?: string;

    cci?: CciTokenSet;

    // existing fields...
}
```

Use whatever naming best matches the existing codebase.

# Refresh logic

Implement CCI-aware access-token refresh.

The existing:

```text
refreshAccessToken()
```

or equivalent internal mechanism must recognize when the current session is using CCI authentication.

Conceptually:

```text
if EU session uses CCI:
    perform CCI token refresh
    update complete CCI token set
    perform CCS token exchange if required
    update session.accessToken
else:
    retain existing legacy behavior
```

The library user must not need to manually refresh anything.

Preserve the existing public behavior around token expiration and automatic refresh.

# CCS2 is NOT the same thing as CCI

Do not confuse these two changes.

CCI / OneApp:

```text
authentication infrastructure
```

CCS2:

```text
vehicle API/protocol variant
```

The official Bluelinky upstream already contains CCS2 support.

Do not replace or rewrite the existing CCS2 implementation unless a concrete compatibility problem is discovered.

The goal of this task is primarily to repair **current EU authentication** and make it feed the existing vehicle API correctly.

# Brand handling

Primary target is:

```text
region = EU
brand = hyundai
```

because this is what we need to run against a real account.

However, inspect the current CCI reference implementations. They contain brand-specific configuration for Hyundai/Kia and possibly Genesis.

Do not unnecessarily hardcode Hyundai-specific values into generic CCI code if a small brand configuration structure can support the others cleanly.

For example, prefer conceptually:

```ts
const config = CCI_CONFIG[this.brand];
```

over scattering things like Hyundai client IDs throughout the implementation.

But do not expand the scope into unrelated brand work if the reference implementations do not support it cleanly.
